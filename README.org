#+TITLE: i915-legacy-oled: OLED brightness for the ThinkPad X1 Yoga on Debian

Brightness control for the OLED panel of the ThinkPad X1 Yoga 1st and 2nd gen under Linux, as a DKMS
module for Debian 14. Stock Linux has none for this panel: =intel_backlight= exists but writing to
it changes nothing.

The driver is Chris Xiong's reverse engineering of Lenovo's Windows "Intel OLED Panel Driver"
([[https://chrisoft.org/blog/post/2025-04-28.html][blog post]],
[[https://git.chrisoft.org/git/linux-legacy-oled-brightness.git][repository]]): a patch to i915 that
drives the panel's brightness over DP AUX with the values of that driver, loaded from a firmware
file. This repository packages it for DKMS. The panel firmware values are the same for both
generations: the =PanelDriver.inf= of Lenovo's Gen 1 package (=n1fdl04w=) and Gen 2 package
(=n1ndp03w=) are byte-identical. The tables that live in the driver binary itself (IRC, SP) could
not be compared that way, but upstream's author states on
[[https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/28][drm/i915/kernel#28]] that both
generations use "the same panel (down to the exact same part number), and the numbers in their
drivers are identical". Confirmed on an X1 Yoga 2nd gen with Debian 14 and 7.2.15+deb14-amd64
(2026-11-09): brightness control works from GNOME with the package installed.

* How it works

The patch changes a structure used all over i915, so the whole =i915.ko= is rebuilt, not a module
next to it. DKMS takes i915 from Debian's own =linux-source= package at build time, never from a
copy in this repository, so the module is Debian's i915 of the same kernel plus the patch.

- =dkms.conf= :: builds =i915.ko= and =kvmgt.ko= (i915's GVT module, built from the same tree with
  the same structures) into =updates/dkms=, which modprobe prefers over the stock ones. A kernel
  whose =linux-source= of the same Debian version is not installed counts as not applicable (DKMS's
  exit 77): no build and no error, so a kernel upgrade never fails over it; the stock i915 is used
  there until the source arrives.
- =prepare-source.sh= :: the DKMS pre-build step: unpacks =drivers/gpu/drm/i915= from
  =/usr/src/linux-source-7.2.tar.xz= and applies the i915 part of upstream's patch and =patches/=,
  checking the version match once more.
- =upstream/= :: upstream's repository as a git submodule, at its commit =a350d0e= (2026-03-28).
  Its files state no license, beyond the two files the patch adds (MIT), so they are not copied
  into this repository: clone with =--recurse-submodules=, or =git submodule update --init=.
- =upstream/linux-legacy-oled-brightness.patch= :: upstream's patch; its hunk for the Xe driver is
  not applied.
- =patches/0002-module-firmware.patch= :: declares the firmware file with =MODULE_FIRMWARE=, so that
  =update-initramfs= copies it into the initramfs next to i915.
- =upstream/gen_panel_prop.py= :: upstream's generator of =intel_legacy_panel_data.bin=, the panel
  values the driver loads; run when the package is built.
- =debian/= :: the =i915-legacy-oled-dkms= package. It depends on =dkms=, =linux-source= and
  =linux-headers-amd64=; installs the DKMS source, the firmware file and
  =/usr/lib/modprobe.d/i915-legacy-oled.conf= (~options i915 enable_dpcd_backlight=99~, what
  upstream's kernel parameter does, without touching the boot loader); builds the module for every
  kernel with headers and refreshes their initramfs. A trigger on =/usr/src= builds it for any
  kernel still without it whenever a package installs there, such as a newer =linux-source= that apt
  unpacked after the kernel.
- =build-deb.sh= :: builds the package in a Debian 14 container (Podman) into =dist/=.
- =test/build.sh= :: builds the package and in a Debian 14 container with the laptop's kernel
  installs it, makes a kernel come before its =linux-source= and lets the trigger build it, and
  removes it; checking modprobe's choice of i915 and the initramfs each time. Output in
  =test/build.log=.

* Install on the laptop

Build the package here (=./build-deb.sh=, in a checkout with its submodule), copy
=dist/i915-legacy-oled-dkms_0.1_all.deb= over and, as root:

#+begin_src sh
apt install ./i915-legacy-oled-dkms_0.1_all.deb
#+end_src

With Secure Boot on (=mokutil --sb-state=), the kernel loads the module only once DKMS's key is
enrolled: =mokutil --import /var/lib/dkms/mok.pub=, choose a one-time password, and confirm it in
the MOK manager at the next boot. Without it i915 fails to load and the screen stays on the
firmware's framebuffer.

After a reboot:

#+begin_src sh
modinfo -n i915                          # .../updates/dkms/i915.ko.xz
dmesg | grep -iE 'legacy|backlight'
ls /sys/class/backlight/                 # intel_backlight; its brightness should now work
#+end_src

=dkms status= shows which kernels have the module. =apt remove i915-legacy-oled-dkms= goes back to
the stock i915, initramfs included.

A real build failure on a future kernel (the patch no longer fitting Debian's i915) still fails that
kernel's installation, as with any DKMS package; =apt remove i915-legacy-oled-dkms= then lets it
through.

* Known issues

At low brightness the screen flickers subtly. Upstream sees brightness become unstable below about
20% on an X1 Yoga 1st gen with an aftermarket OLED panel, and the same with Lenovo's driver on
Windows; it shows on a factory-fitted 2nd gen too (2026-11-09), though that panel has a history of
failing (replaced several times under warranty, flickering among the symptoms). What most of the
panel's registers do is unknown.

History: Intel's 2019 patch "drm/i915: customize DPCD brightness control for specific panel" (Lee
Shawn C, never merged) was once pointed to on bug 97883 / #28 as a fix for this panel, but it
handles a 2019 Samsung panel through the registers i915 now supports as the Intel HDR backlight
interface; the 2016-2018 panels use the older protocol this patch implements.
