#+TITLE: i915-legacy-oled: OLED brightness for the ThinkPad X1 Yoga on Debian

Brightness control for the OLED panel of the ThinkPad X1 Yoga 1st and 2nd gen under Linux, as a DKMS
module for Debian 14. Stock Linux has none for this panel: =intel_backlight= exists but writing to
it changes nothing.

The driver is Chris Xiong's reverse engineering of Lenovo's Windows "Intel OLED Panel Driver"
([[https://chrisoft.org/blog/post/2025-04-28.html][blog post]],
[[https://git.chrisoft.org/git/linux-legacy-oled-brightness.git][repository]]): a patch to i915 that
drives the panel's brightness over DP AUX with the values of that driver, loaded from a firmware
file. This repository packages it for DKMS, through a fork of that repository,
[[https://github.com/muusik/oled_pwm_extract_panel_prop][oled_pwm_extract_panel_prop]], which adds a
generator of the panel values from Lenovo's driver package (offered back to upstream). The panel
firmware values are the same for both generations: the =PanelDriver.inf= of Lenovo's Gen 1 package
(=n1fdl04w=) and Gen 2 package (=n1ndp03w=) are byte-identical. The tables that live in the driver
binary itself (IRC, SP) could not be compared that way, but upstream's author states on
[[https://gitlab.freedesktop.org/drm/i915/kernel/-/work_items/28][drm/i915/kernel#28]] that both
generations use "the same panel (down to the exact same part number), and the numbers in their
drivers are identical". Confirmed on an X1 Yoga 2nd gen with Debian 14 and 7.2.15+deb14-amd64
(2026-11-09): brightness control works from GNOME with the package installed.

* How it works

The patch changes a structure used all over i915, so the whole =i915.ko= is rebuilt, not a module
next to it. DKMS takes i915 from Debian's own =linux-source= package at build time, never from a
copy in this repository, so the module is Debian's i915 of the same kernel plus the patch.

- =dkms.conf= :: builds =i915.ko= and =kvmgt.ko= (i915's GVT module, built from the same tree with
  the same structures) into =updates/dkms=, which modprobe prefers over the stock ones. A kernel
  whose =linux-source= of the same Debian version is not installed counts as not applicable (DKMS's
  exit 77): no build and no error, so a kernel upgrade never fails over it; the stock i915 is used
  there until the source arrives.
- =prepare-source.sh= :: the DKMS pre-build step: unpacks =drivers/gpu/drm/i915= from
  =/usr/src/linux-source-<major.minor>.tar.xz= and applies the i915 part of upstream's patch and
  =patches/=, checking the version match once more. Upstream's hunk for i915's =Makefile= is left
  out, as its context changes between kernels (7.3 added =intel_dp_link_caps.o=): the script adds
  the object after =intel_dp_aux_backlight.o= itself.
- =upstream/= :: the fork
  [[https://github.com/muusik/oled_pwm_extract_panel_prop][oled_pwm_extract_panel_prop]] as a git
  submodule: upstream at its commit =a350d0e= (2026-03-28) plus =extract_panel_prop.py= (with its
  x86-64 decoder =x86_64_decode.py=) and =download_panel_prop.sh= (MIT), which generate the panel
  values from Lenovo's driver package instead of numbers kept in a script. Upstream's files state no
  license, beyond the two files the patch adds (MIT), so they are not copied into this repository:
  clone with =--recurse-submodules=, or =git submodule update --init=.
- =upstream/linux-legacy-oled-brightness.patch= :: upstream's patch; its hunk for the Xe driver is
  not applied.
- =patches/0002-module-firmware.patch= :: declares the firmware file with =MODULE_FIRMWARE=, so that
  =update-initramfs= copies it into the initramfs next to i915.
- =i915-legacy-oled-fetch= :: generates =/usr/lib/firmware/intel_legacy_panel_data.bin=, the panel
  values the driver loads, on the laptop when the package is installed: it downloads Lenovo's driver
  package =n1ndp03w.exe= (URL and SHA-256 as in =upstream/download_panel_prop.sh=), keeps it in
  =/var/cache/i915-legacy-oled=, checks its SHA-256 before every use and runs
  =upstream/extract_panel_prop.py= on it, whose output is byte for byte that of upstream's
  =gen_panel_prop.py= (which keeps the values in the script and is not used). The values come from
  Lenovo's driver, which carries no license to redistribute it, so the package does not ship them
  but generates them on the machine, as Debian's contrib installer packages
  (=firmware-b43-installer=) do with such firmware. Run it as root to retry after a failed download;
  it refreshes the initramfs of every kernel.
- =debian/= :: the =i915-legacy-oled-dkms= package. It depends on =dkms=, =linux-source= and
  =linux-headers-amd64=, and on =innoextract=, =python3= and =curl= for the panel data; installs the
  DKMS source, the panel data extractor and =/usr/lib/modprobe.d/i915-legacy-oled.conf=
  (~options i915 enable_dpcd_backlight=99~, what upstream's kernel parameter does, without touching
  the boot loader); builds the module for every kernel with headers and refreshes their initramfs. A
  trigger on =/usr/src= builds it for any kernel still without it whenever a package installs there,
  such as a newer =linux-source= that apt unpacked after the kernel.
- =build-deb.sh= :: builds the package into =dist/= with the machine's own Debian tools (the
  =Build-Depends= of =debian/control=, on Debian 14). In a bread_ladder session, those of its
  =debian-forky= toolset (=.bl-tools=).
- =test/build.sh= :: builds the package and in a Debian 14 container with the laptop's kernel
  installs it, makes the panel data download fail and retries it from the cache, makes a kernel come
  before its =linux-source= and lets the trigger build it, and removes it; checking modprobe's
  choice of i915 and the initramfs each time; purges it last. Output in =test/build.log=. Lenovo's
  driver package is downloaded by the first run only, into =~/.cache/oled_pwm= (=$XDG_CACHE_HOME=),
  and given to the package's cache in the container after that. Runs on the host, with its Podman: a
  bread_ladder session has none.

* Install on the laptop

Build the package here (=./build-deb.sh=, in a checkout with its submodule), copy
=dist/i915-legacy-oled-dkms_0.2_all.deb= over and, as root:

#+begin_src sh
apt install ./i915-legacy-oled-dkms_0.2_all.deb
#+end_src

The installation downloads Lenovo's driver package (about 330 KB, through =https_proxy= if set),
unless =/var/cache/i915-legacy-oled= already has it; purging the package removes that cache. Without
the network it still installs, without the panel data and so without brightness control;
=i915-legacy-oled-fetch= then retries.

With Secure Boot on (=mokutil --sb-state=), the kernel loads the module only once DKMS's key is
enrolled: =mokutil --import /var/lib/dkms/mok.pub=, choose a one-time password, and confirm it in
the MOK manager at the next boot. Without it i915 fails to load and the screen stays on the
firmware's framebuffer.

After a reboot:

#+begin_src sh
modinfo -n i915                          # .../updates/dkms/i915.ko.xz
dmesg | grep -iE 'legacy|backlight'
ls /sys/class/backlight/                 # intel_backlight; its brightness should now work
#+end_src

=dkms status= shows which kernels have the module. =apt remove i915-legacy-oled-dkms= goes back to
the stock i915, initramfs included.

A real build failure on a future kernel (the patch no longer fitting Debian's i915) still fails that
kernel's installation, as with any DKMS package; =apt remove i915-legacy-oled-dkms= then lets it
through.

* Known issues

At low brightness the screen flickers subtly. Upstream sees brightness become unstable below about
20% on an X1 Yoga 1st gen with an aftermarket OLED panel, and the same with Lenovo's driver on
Windows; it shows on a factory-fitted 2nd gen too (2026-11-09), though that panel has a history of
failing (replaced several times under warranty, flickering among the symptoms). What most of the
panel's registers do is unknown.

The panel itself degrades, and no driver can fix that. Owners of the X1 Yoga 2nd gen report the same
course
([[https://forums.lenovo.com/t5/ThinkPad-X-Series-Laptops/Yoga-X1-OLED-Gen-2-OLED-screen-failure-support-request/m-p/5124686][Lenovo Community thread]],
saved in =reference/=): flickering and banding that start in cool air (below about 17 °C) and get
worse within hours, first at low brightness and then higher up; the panel works again for minutes
when warmed, and for weeks or months after resting unused; replacement panels, original Samsung
parts included, fail the same way, some within months. The explanation given there, by an owner who
worked in thin-film solar panels, is the bond between the panel glass and its flex cable or driver
chip: the contacts there are not soldered but glued with an anisotropic conductive film, an adhesive
with metal-coated particles that connect a pad only while the adhesive keeps them pressed. Aged by
humidity and temperature cycles, the adhesive holds them less tightly, cold shrinks it further, and
contacts turn intermittent or resistive: bands from signal lines, and flicker from the power feeds,
which on an OLED carry the whole screen's current. Warmth presses the particles again; reflowing
does nothing, there is no solder. This fits the symptoms but is not confirmed for this panel.
Studies of these films under damp heat find the same direction: the adhesive swells, water creeps
along the interface, contact resistance rises and joints open. None was found on cold alone.
Lenovo's only support note on the flicker (HT506966, 2018, saved in =reference/=) predates most
failures: it blames panel self refresh at brightness 0 and says no hardware replacement is needed.

No one seems to have opened the panel itself and looked at its bonds (as of 2026-11). Chris Xiong's
[[https://chrisoft.org/blog/post/2025-04-16.html][refurbishing post]] gives the OLED parts (display
assembly 01AW977, driver board 00NY439, cable 01AW979) but nothing inside the panel, and iFixit's
display teardown does not say it is the OLED variant. Such a panel usually has two bonds of this
kind, either of which could be the failing one: the flex cable on the glass edge, coarse enough that
TV and phone repair shops rebond it routinely, and the driver chip on the glass, several times finer
and beyond repair outside a factory.

Replacing the adhesive is possible in principle and a long shot in practice. Re-pressing the old
bond with a heated flat tool (around 120 °C is suggested on repair forums) is cheap, but the cured
epoxy only partly regains its grip, and OLED material and its thin seal tolerate little heat. A full
rebond means peeling the flex, cleaning the pads, laying new film, aligning under a microscope and
hot-pressing at around 180-200 °C; bonding machines cost about $500-5500, and a failed bond on a
panel no longer made is final. Replacement panels (about $100) carry adhesive of the same age.
Before any of this, check it is the bond: while the screen flickers, press gently along the edge
where the flex leaves the glass, and warm only that edge, then only the middle. A change from the
edge alone points at the bond; one only from warming the whole panel points elsewhere.

History: Intel's 2019 patch "drm/i915: customize DPCD brightness control for specific panel" (Lee
Shawn C, never merged) was once pointed to on bug 97883 / #28 as a fix for this panel, but it
handles a 2019 Samsung panel through the registers i915 now supports as the Intel HDR backlight
interface; the 2016-2018 panels use the older protocol this patch implements.

* Test

#+begin_src sh
test/build.sh [kernel version]
#+end_src

Run it on the host: it needs Podman for the test container, which bread_ladder sessions do not have
(=.bl-tools= no longer selects the =podman= toolset). It builds the package with =build-deb.sh=
first when =dpkg-buildpackage= is there; without it, it tests the =.deb= already in =dist/=, built
in a session with =./build-deb.sh=. With =BL_APT_PROXY= set to an apt-cacher-ng
(=http://host:3142=), the image's apt goes through it; without it, straight to Debian's mirrors.
